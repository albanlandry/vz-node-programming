Interactive Node Execution Flow

Last Updated: 2025-01-07

This document provides a comprehensive, detailed explanation of the interactive node execution process between the frontend and backend, including complete flow diagrams and implementation details.

📋 Overview: Interactive nodes allow graph execution to pause and request user input, display images, or stream data in real-time. This document explains the complete end-to-end flow from execution initiation to completion.

Phase 1: Execution Initiation (Frontend → Backend)

1. User Triggers Execution

User clicks the "Execute" button in the ExecutionToolbar component.

  • Component: components/graph/ExecutionToolbar.tsx
  • Function: handleStreamingExecution()
  • Action: Collects graph definition, inputs, and execution options

2. Frontend Establishes SSE Connection

StreamingExecutionService.executeStream() is called:

POST /api/graphs/execute-stream Content-Type: application/json { "graph": { /* GraphDefinition */ }, "inputs": { /* Optional initial inputs */ }, "options": { /* Execution options */ } }
  • Service: services/streamingExecutionService.ts
  • Response: ReadableStream for Server-Sent Events (SSE)

3. Frontend Starts Reading SSE Stream

The frontend continuously reads from the stream:

  • Uses response.body.getReader() to read chunks
  • Decodes bytes using TextDecoder
  • Parses SSE format: event: <type>\ndata: <json>\n\n
  • Emits events to registered listeners via streamingExecutionService.emit()
// Example SSE event format event: execution:started data: {"executionId":"exec-1234567890-abc","timestamp":1234567890} event: node:executing data: {"nodeId":"node-1","executionId":"exec-1234567890-abc"}

Phase 2: Backend Execution Setup

4. Backend Creates Execution Context

The POST /api/graphs/execute-stream handler starts:

  • Generates unique executionId: exec-${Date.now()}-${random}
  • Creates GraphExecutionEngine instance
  • Calls engine.buildExecutor(graph) to build the executor
let executionId = `exec-${Date.now()}-${Math.random().toString(36).substr(2, 9)}`; const engine = new GraphExecutionEngine(); const executor = await engine.buildExecutor(graph);

5. Executor Registration (Critical Timing)

⚠️ Critical: Executor must be registered BEFORE sending execution:started event to ensure it's available when client receives the executionId.

Executor is registered in activeExecutors Map:

  • Key: executionId
  • Value: NodeExecutor instance
// Register executor BEFORE sending execution:started registerExecutor(executionId, executor);

6. Backend Sends execution:started Event

SSE event sent to frontend:

event: execution:started data: { "executionId": "exec-1234567890-abc", "timestamp": 1234567890 }

Frontend receives this and stores the executionId for later use.

7. Backend Sets Up Event Listeners

Registers listeners on the executor for various event types:

  • NodeEventType.EXECUTION_STARTED
  • NodeEventType.EXECUTION_COMPLETED
  • NodeEventType.EXECUTION_FAILED
  • InteractiveNodeEventType.USER_INPUT_REQUESTED
  • InteractiveNodeEventType.USER_INPUT_RECEIVED
  • InteractiveNodeEventType.NODE_PAUSED
  • InteractiveNodeEventType.NODE_RESUMED

Each listener forwards events as SSE to the frontend.

8. Backend Begins Graph Execution

Calls either:

  • executor.execute(initialInputs) - Sequential execution
  • executor.executeParallel(initialInputs) - Parallel execution

The executor processes nodes in topological order (sequential) or concurrently (parallel).

Phase 3: Interactive Node Execution (Backend)

9. Executor Identifies Interactive Node

In NodeExecutor.executeNode():

  • Checks isInteractiveNode(node) - verifies node implements IInteractiveNode
  • If interactive, creates InteractiveExecutionContext
const isInteractive = this.isInteractiveNode(node); if (isInteractive) { const interactiveContext = new InteractiveExecutionContext( baseContext, this, // EventEmitter nodeId ); }

10. Interactive Context Creation

InteractiveExecutionContext wraps the base ExecutionContext:

  • Stores inputResolver: Promise resolver for user input
  • Stores inputRejecter: Promise rejecter for cancellation
  • Stores nodeId: Node identifier

Context is stored in executor.interactiveContexts Map for later retrieval.

11. Interactive Node Execution

Calls node.executeInteractive(interactiveContext) instead of regular node.execute().

For custom interactive nodes (CustomNode with expression === 'ui'):

  • Retrieves uiConfig from node properties or constructor
  • Retrieves uiDefinition from node properties or storage
  • Builds UserInputRequest with:
    • type: 'form'
    • formSchema: Fields derived from UI definition components
    • uiDefinitionId: ID for frontend to load custom UI
    • content: Optional content to display

12. User Input Request

Node calls context.requestUserInput(request):

async requestUserInput(request: UserInputRequest): Promise<unknown> { return new Promise((resolve, reject) => { this.inputResolver = resolve; this.inputRejecter = reject; // Emit event: Display input request in UI this.eventEmitter.emit( InteractiveNodeEventType.USER_INPUT_REQUESTED, { nodeId, executionId, request } ); // Emit event: Pause node this.eventEmitter.emit( InteractiveNodeEventType.NODE_PAUSED, { nodeId, executionId } ); }); }

Execution pauses here - the Promise is returned and awaits resolution.

13. Backend Forwards Events to Frontend

Executor's event listener catches USER_INPUT_REQUESTED:

  • Sends SSE event: event: interactive:user-input-requested
  • Data: { nodeId, executionId, request, timestamp }
  • Also sends: event: interactive:node-paused

Phase 4: Frontend UI Display

14. Frontend Receives User Input Request

Flow:

  1. StreamingExecutionService receives SSE event
  2. Parses and emits to listeners
  3. InteractiveNodeManager component listens for interactive:user-input-requested

15. Frontend Displays Input Dialog

InteractiveNodeManager.handleUserInputRequested() is called:

  • Sets pendingInput state: { nodeId, executionId, request }
  • Component re-renders and shows dialog

Dialog Selection Logic:

  • If request.uiDefinitionId exists OR node has uiConfig: Uses UIDialog
  • Otherwise: Uses UserInputDialog

16. UI Dialog Rendering

UIDialog (Custom UI):

  • Loads UI definition from uiBuilderStore using uiDefinitionId
  • Renders form using UIRenderer component
  • Displays custom UI components (inputs, textareas, selects, etc.)

UserInputDialog (Standard Form):

  • Renders standard form based on request.formSchema

Phase 5: User Input Submission (Frontend → Backend)

17. User Fills Form and Submits

User interacts with form fields and clicks "Submit" button:

  • UIDialog or UserInputDialog calls onSubmit(formData)

18. Frontend Sends Input to Backend

InteractiveNodeManager.handleSubmit() is called:

POST /api/graphs/interactive/input/${nodeId} Content-Type: application/json { "executionId": "exec-1234567890-abc", "value": { /* form data */ } }

value contains the form data (object or single value).

19. Backend Receives User Input

POST /api/graphs/interactive/input/[nodeId] handler:

  1. Extracts executionId and value from request body
  2. Looks up executor: activeExecutors.get(executionId)
  3. If executor not found: Returns 404 "Execution not found or expired"
  4. If found: Calls executor.provideUserInput(nodeId, value)

20. Backend Provides Input to Node

NodeExecutor.provideUserInput():

  1. Retrieves InteractiveExecutionContext from interactiveContexts.get(nodeId)
  2. Calls context.provideUserInput(value)

Inside InteractiveExecutionContext.provideUserInput():

  • Calls stored inputResolver(value) → resolves the Promise
  • Clears inputResolver and inputRejecter
  • Emits USER_INPUT_RECEIVED event
  • Emits NODE_RESUMED event

21. Node Execution Resumes

The Promise from requestUserInput() resolves with the user's input:

  • Node continues execution
  • Validates input (if validateBeforeSubmit is true)
  • Maps form data to outputs using outputMapping
  • Returns ExecutionResult with outputs

22. Backend Forwards Resume Events

Executor's listeners catch USER_INPUT_RECEIVED and NODE_RESUMED:

  • Sends SSE events to frontend:
    • event: interactive:user-input-received
    • event: interactive:node-resumed

Phase 6: Execution Continuation

23. Frontend Updates UI

Receives interactive:user-input-received event:

  • InteractiveNodeManager clears pendingInput state
  • Dialog closes automatically

24. Graph Execution Continues

Node execution completes:

  • Outputs are propagated to connected nodes
  • Next nodes in the graph execute
  • Process repeats until all nodes complete

25. Execution Completion

When all nodes finish:

  • Backend sends execution:completed SSE event
  • Unregisters executor: unregisterExecutor(executionId)
  • Closes SSE stream

Frontend receives completion event and updates UI.

Critical Implementation Details

1. Executor Registration Timing

Critical: Executor must be registered BEFORE execution:started is sent. This ensures the executor is available when the client receives the executionId.

// ✅ CORRECT: Register before sending event registerExecutor(executionId, executor); sendEvent('execution:started', { executionId }); // ❌ WRONG: Register after sending event sendEvent('execution:started', { executionId }); registerExecutor(executionId, executor); // Too late!

2. Promise-Based Pausing

requestUserInput() returns a Promise that resolves when provideUserInput() is called. This pauses execution without blocking the event loop.

// Node execution pauses here const userInput = await context.requestUserInput(request); // Execution resumes when provideUserInput() is called // with the user's input value

3. Event-Driven Architecture

Uses EventEmitter pattern for loose coupling between components:

  • Backend: NodeExecutor emits events
  • Backend: execute-stream route forwards as SSE
  • Frontend: StreamingExecutionService emits to listeners
  • Frontend: InteractiveNodeManager handles events

4. State Management

Frontend uses React state (pendingInput) to track active input requests. Backend uses Maps to track active executors and interactive contexts.

5. Error Handling

If executor is not found (404), the dialog stays open for retry. Cancellation is handled via cancelUserInput().
